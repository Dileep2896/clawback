## What I found
- `call_provider` (packages/agents/src/tools/negotiator.ts) is the one gated Negotiator tool. It waits on the approval gate, places a sim/live call, stores a `calls` row (transcript + `outcomeJson` = `{cancelled_lines, credits, ticket}`), marks the call action done. `cancel_service` and `plan-check.ts` read only `calls.outcomeJson`; Finance reads finding statuses. So if the email path writes the same `calls` row shape, cancel_service, plan-check, Finance, ledger and Overview need no change.
- The call action payload is `{accountNumber, cancelLines, promoAccounts}`; `promoAccounts` is always `[]` (approver.ts:89, human's rehearsal decision). The email covers line cancellations only.
- `callFacts` (services/voice/src/facts.ts) already builds holder, company, approval date and the owner/automatic wording from the database. The email reuses it, and `checkPlan` (alarm lines refused).
- `approvals.channel` already means how the owner approved (dashboard/sms/naive). The contact choice needs its own field.
- Mail adapter (local): Mailpit via nodemailer, recipient must pass `ALLOWED_EMAIL_DOMAINS` (`billfighter.local,goldengatenoodle.example` today). It has no inbox read; Mailpit's HTTP API (`MAILPIT_API`) is already used by scripts and tests.
- Demo runs go through `pnpm dev:webhooks`; `pnpm run:local` runs in-process.
- agents-redesign holds the amber approval card (`components/agents/approval.tsx`), `use-approve.ts`, the Negotiator call view (`components/agents/call.tsx`) and `lib/tool-words.ts`. Not on main yet: I merge it first and again at the end.
