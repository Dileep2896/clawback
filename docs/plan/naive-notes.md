## One approval releases the bundle (written answer)

naïve has no bundle confirm. `ApprovalGate` stays **ours**, and naïve's `ask` is driven from it. Source: [concepts/policies](https://usenaive.ai/docs/concepts/policies.md), [api/sessions](https://usenaive.ai/docs/api/sessions.md), [api/events](https://usenaive.ai/docs/api/events.md), [team/context-and-budgets](https://usenaive.ai/docs/team/context-and-budgets.md), [sdk/sessions](https://usenaive.ai/docs/sdk/sessions.md).

1. Gated tools get `permission: "ask"` on **every agent that has them** (coordinator and each roster member: policy is per agent, see note 8). Every other tool gets `allow`. A gated call parks **the session that made it**: `status: idle`, `stop_reason: awaiting_approval`, and `pending_actions[]` rows with `kind: "tool"`, `tool_call_id`, `name` and `args`. An unanswered `ask` waits for hours and costs no budget while it waits.
2. Linda approves our `approvals` row once, by dashboard tap or by SMS YES (see Q2). This is the single human decision, recorded with `channel` and `approvedBy`.
3. **Which sessions to watch.** A delegated member (`send_to_agent`, `wait: true`) runs as **its own session**, a thread with `parent_session_id` = the coordinator's session and its own event stream. Its parked call is on the member session, not on the coordinator's. The coordinator meanwhile shows `awaiting_delegation`, not `awaiting_approval`. The adapter therefore tracks the whole run tree:
   - the root session it created;
   - every member session, found from the root's `thread.created` events (`thread_id`, `agent_id`, `member`) and reconciled with `client.sessions.threads(rootId)` (`GET /v1/sessions/{id}/threads`);
   - and every board-started session: a card assigned on the board starts a **top-level** session of that agent (no `root_session_id`), whose id the card returns as `woken_session_id` and whose `metadata.board` is `{ card_id, board_id }`. The adapter records the card ids the run creates and takes each card's `woken_session_id`.
   **Ownership is explicit.** Each run records every naïve session id it starts or learns this way (root, members, board-woken) in our DB against the run id. The loop only confirms or denies calls on sessions recorded for that run. It never matches by agent id or start time, and never touches any other session, parked or not. One run at a time is also the demo rule (`demo:reset` before each run).
4. **The decision rule**, applied to each `kind: "tool"` row on a session recorded for this run, keyed by the `actionId` our MCP tool puts in `args`:
   - bundle **approved** and `actionId` in it → `confirmTool(sid, { tool_call_id, decision: "allow" })`;
   - bundle **pending** (Linda has not answered) → **do nothing**. The call stays parked. The adapter rechecks every parked row when our `approvals` row changes (written by `apps/dashboard/app/api/approve`) and on each new `session.idle` with `awaiting_approval`;
   - bundle **rejected**, `actionId` not in any bundle of this run, or no `actionId` at all → `decision: "deny"` with a `reason`.
   The adapter branches on `kind`, never on `name`, as the docs warn. Later gated calls in the same run, on the coordinator or any member, park again and are released by the same rule against the **same** approved bundle, so Linda never sees a second prompt. `scope: "session"` is not used: it grants a tool name for one session only, not across members.
5. naïve records our API key (`key_0mp9e160jnt6ns4afanysvjzjd`) as `actor` on each `tool.confirm.resolved` event. The person is in our `approvals` row, and the adapter writes both to `audit_log`.

**Verified so far:** the routes exist and answer (`/v1/sessions?stop_reason=awaiting_approval` 200, `/v1/sessions/{id}/threads` 404 "no such session" for a fake id). **Not verified live:** that a member's `ask` parks the member session and leaves the coordinator at `awaiting_delegation`. The org has no agents yet. `naive-runtime-adapter` must test it with one gated member call before it builds the loop.
